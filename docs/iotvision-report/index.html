บทนำ

IotVision คือแพลตฟอร์มแดชบอร์ดสำหรับงานอุตสาหกรรม (Industrial IoT) ที่รวมการเฝ้าติดตามข้อมูลจากเครื่องจักรแบบเรียลไทม์ การสร้างแดชบอร์ดปรับแต่งได้ด้วยการลากวาง การแจ้งเตือนตามเกณฑ์ โหมดจอ LED สำหรับหน้างาน และผู้ช่วยปัญญาประดิษฐ์ (AI) เข้าไว้ในระบบเดียว

วัตถุประสงค์ของเอกสาร

เอกสารฉบับนี้อธิบายการทำงานของระบบ IotVision ทั้งมุมมองผู้ใช้งานและมุมมองทางเทคนิค โดยเน้นรายละเอียดของโมดูลผู้ช่วย AI เป็นพิเศษ เพื่อให้ผู้อ่านเข้าใจทั้งวิธีใช้งานและหลักการเบื้องหลัง

ที่มาและความสำคัญ

โรงงานอุตสาหกรรมสร้างข้อมูลจากเซนเซอร์จำนวนมากอย่างต่อเนื่อง การนำข้อมูลมาแสดงผลและวิเคราะห์ได้ทันเวลาจึงจำเป็นต่อการตัดสินใจ IotVision ออกแบบมาเพื่อรับข้อมูลเทเลเมทรีความถี่สูง จัดเก็บด้วยฐานข้อมูลอนุกรมเวลา และนำเสนอผ่านแดชบอร์ดที่ปรับแต่งได้เอง พร้อมผู้ช่วย AI ที่ตอบคำถามจากภาษาธรรมชาติ

ภาพรวมการทำงาน

ระบบรองรับหลายองค์กร (Multi-tenant) จัดโครงสร้างเป็นลำดับชั้น องค์กร → โรงงาน → สายการผลิต → เครื่องจักร อุปกรณ์หน้างานส่งข้อมูลผ่าน REST ระบบประเมินการแจ้งเตือนและกระจายข้อมูลไปยังผู้ใช้ที่เชื่อมต่ออยู่ผ่าน WebSocket ทันที ทำให้แดชบอร์ดอัปเดตแบบเรียลไทม์

หน้าการแจ้งเตือนแบ่งเป็นแท็บ เหตุการณ์ (Events) · กฎ (Rules) · สด (Live) ผู้ใช้กำหนดกฎการแจ้งเตือนได้จากเงื่อนไข เครื่องจักร + ฟิลด์ + เงื่อนไขเปรียบเทียบ + ค่าเกณฑ์ + ระดับความรุนแรง พร้อมกำหนดช่วงเวลาหน่วง (cooldown) เพื่อป้องกันการแจ้งซ้ำถี่เกินไป

วงจรสถานะของเหตุแจ้งเตือน

เมื่อเงื่อนไขถูกละเมิด ระบบจะบันทึกเหตุการณ์ลงตาราง alert_events โดยมีวงจรสถานะ เปิด (open) → รับทราบ (acknowledged) → แก้ไขแล้ว (resolved) ผู้ใช้สามารถกดแก้ไขทีละรายการหรือทั้งหมดได้

การประเมินการแจ้งเตือนถูกเรียกทั้งตอนรับข้อมูลเข้า (ingest) และโดยตัวกระจายข้อมูล (broadcaster) ที่ตรวจซ้ำทุก 30 วินาที การหน่วง (cooldown) บังคับใช้ในฝั่งบริการเพื่อระงับการยิงซ้ำภายในช่วงเวลาที่กำหนด

1.7 โหมด LED (จอหน้างาน)

ที่อยู่: /led (เข้าถึงได้โดยไม่ต้องล็อกอิน)

โหมด LED เป็นหน้าจอสำหรับติดตั้งที่หน้างานโรงงาน แสดงผลเต็มจอขนาด 640×320 พิกเซล ไม่มีเมนูหรือส่วนควบคุม เหมาะกับจอ LED ขนาดใหญ่ ข้อมูลอัปเดตต่อเนื่องผ่าน WebSocket โดยไม่ต้องมีผู้ดูแลคอยรีเฟรช

ตัวอย่างจอ LED ต้องสร้างลิงก์ที่มีโทเคนและผังวิดเจ็ต (base64) ก่อน จึงไม่สามารถจับภาพหน้าเปล่าได้
(ใช้ปุ่ม “Export LED Link” จากตัวแก้ไขแดชบอร์ดเพื่อสร้างภาพจริง แล้วบันทึกทับไฟล์ images/ui/08-led.png)

การสร้างและเพิกถอนลิงก์

  • ผู้มีสิทธิ์ (admin/editor) สร้างโทเคนถาวร (บทบาท led-viewer ไม่มีวันหมดอายุ) ผ่าน POST /api/led/token เก็บไว้ในคอลัมน์ organizations.led_token
  • ปุ่ม "Export LED Link" สร้างลิงก์รูปแบบ /led?w=<ผังวิดเจ็ต base64>&token=<led-jwt>
  • เพิกถอนด้วย DELETE /api/led/token และสร้างใหม่เพื่อหมุนเวียนโทเคน
ลิงก์ LED ฝังโทเคนที่ให้สิทธิ์อ่านข้อมูลขององค์กร ควรจำกัดการเผยแพร่และหมุนเวียนโทเคนเมื่อจำเป็น

1.8 ผู้ช่วย AI — ถามข้อมูล (Ask Data)

ที่อยู่: /ask (ข้อมูลสาธิต) · /nj5 (โรงงานจริง)

หน้า "ถามข้อมูล" ให้ผู้ใช้พิมพ์คำถามเป็นภาษาธรรมชาติ (ไทยหรืออังกฤษ) แล้วระบบจะสร้างกราฟ ตาราง หรือคำตอบเชิงบรรยายเพื่อตอบคำถามนั้น เหมาะสำหรับการสำรวจข้อมูลอย่างรวดเร็วโดยไม่ต้องสร้างวิดเจ็ตเอง

เลือกชุดข้อมูลก่อนถาม

แถบ "DATA" เหนือช่องพิมพ์คือชุดข้อมูลที่จะใช้ตอบ — Demo telemetry (ข้อมูลสาธิต) หรือ ชื่อโรงงาน เช่น Nongjok5 (ข้อมูลจริงหน้างาน) หนึ่งคำถามตอบจากหนึ่งโรงงานเสมอ สลับชุดแล้วที่อยู่หน้าเว็บและเมนูซ้ายเปลี่ยนตาม จึงบุ๊กมาร์กได้ตรงชุด

รูปแบบการตอบ 3 แบบ

  • ตอบด้วยข้อมูล — แสดงผลเป็นกราฟหรือตาราง
  • ถามกลับ — เมื่อคำถามกำกวม ระบบถามเพื่อให้ระบุให้ชัดเจน
  • คำอธิบายเชิงบรรยาย — สรุป/อธิบายกราฟปัจจุบัน อ้างอิงข้อมูลจริงที่เพิ่งดึงมา

ตัวอย่างคำถาม

  • "ค่าน้ำหนักเฉลี่ยรายชั่วโมงของ CW-01 วันนี้" → กราฟเส้น
  • "อุณหภูมิ evap ของ IQF2 เทียบกับยอดผลิต เดือนมิถุนายน" → กราฟสองแกน (แท่ง = ยอดผลิต, เส้น = อุณหภูมิ)
  • "รายชื่อเครื่องจักรทั้งหมด" → ตาราง
อ่านกราฟให้ถูก — แถบจาง รอบเส้นคือช่วงต่ำสุด–สูงสุดในแต่ละช่วงเวลา เส้นกลางคือค่าเฉลี่ย: ชั่วโมงที่เครื่องวิ่ง −35°C แล้วละลายน้ำแข็งขึ้น +25°C ค่าเฉลี่ยจะออกมาราว +1.6°C ซึ่งเครื่องไม่เคยอยู่ที่ค่านั้นจริง แถบจึงบอกสิ่งที่ค่าเฉลี่ยเดียวซ่อนไว้ · เส้นขาด = ต้นทางไม่ส่งข้อมูลช่วงนั้น ไม่ใช่ค่าศูนย์ · Boards บันทึกกราฟไว้เป็นชุด เปิดใหม่แล้วระบบสร้างคำสั่งขึ้นใหม่จาก "เจตนา" ที่บันทึกไว้ จึงได้ค่าล่าสุดเสมอและไม่พังเมื่อโครงสร้างข้อมูลเปลี่ยน

ผู้ช่วยแชทเป็นตัวแทน (Agent) ที่อ่านข้อมูลเทเลเมทรีสดและช่วยจัดการแดชบอร์ดผ่านการสนทนา จุดเด่นคือกลไก "พรีวิวก่อนยืนยัน" (Preview then Confirm) ผู้ช่วยจะจัดเตรียมการเปลี่ยนแปลงเป็นพรีวิวให้ตรวจสอบก่อน แล้วจึงบันทึกจริงเมื่อผู้ใช้กดยืนยัน

  • ดูเหตุแจ้งเตือนที่เปิดอยู่

ภาพรวมขั้นตอน — การจับคู่เจตนากับเครื่องมือ (cases) และการให้คะแนนคำตอบ อยู่ในหน้าถัดไป

ขั้นตอนหลัก

  • จำแนกเจตนา — เรียกโมเดล Router ครั้งเดียว หากความเชื่อมั่นต่ำกว่า 0.5 หรือจำแนกไม่ได้ จะกลับไปใช้โหมดเลือกเครื่องมืออัตโนมัติ
  • ตัดสินด้วย Go — จับคู่เจตนากับเครื่องมือที่ต้องบังคับเรียก (deterministic) เช่น อ่านค่า→show_metric, ผลิต→get_production_count
  • วนเรียกเครื่องมือ — สูงสุด 5 รอบ เมื่อครบเพดานจะตัดเครื่องมือออกเพื่อบังคับให้สรุปเป็นข้อความ
  • ตรวจสอบแล้วซ่อม — ตรวจเชิงกำหนด (deterministic) และให้โมเดลตรวจคำตอบ ก่อนส่ง/ถามกลับ/ซ่อมหนึ่งรอบ
ผู้ใช้บทบาท viewer จะไม่ถูกบังคับเรียกเครื่องมือกลุ่มแก้ไข (preview_*) เครื่องมือกลุ่มนี้ต้องเป็น admin หรือ editor เท่านั้น

2.6 กลไก Ask Data (NL → SQL → กราฟ)

หน้า Ask Data (POST /api/ai/ask) แปลงคำถามภาษาธรรมชาติเป็นคำสั่งอ่านข้อมูลอย่างเดียว รันกับข้อมูลจริง แล้วให้โมเดลออกแบบกราฟ ECharts จากผลลัพธ์ โดยมีการตรวจสอบในทุกขั้น เส้นทางต้นทางแยกตามชุดข้อมูล — ชุดสาธิตให้โมเดลเขียน SQL แล้วตรวจ ส่วนชุดข้อมูลโรงงานจริงให้โมเดลส่งเพียง "เจตนา" (query spec) แล้วเซิร์ฟเวอร์เขียน SQL เอง ครึ่งหลังของกระบวนการ (วาดกราฟ ตรวจคะแนน ซูม บันทึก Board) ใช้ร่วมกันทั้งสองเส้นทาง

มาตรการความปลอดภัยของการอ่านข้อมูล

  • คำสั่งที่โมเดลเขียนเอง: อนุญาตเฉพาะ SELECT เดี่ยว และเข้าถึงได้เพียง 5 view — v_telemetry, v_machines, v_machine_fields, v_series, v_readings ตารางฐานทั้งหมดถูกปฏิเสธ
  • คำสั่งที่เซิร์ฟเวอร์คอมไพล์: ค่าทุกค่าที่มาจากโมเดลถูกส่งเป็นพารามิเตอร์ (bind) ไม่มีการต่อสตริง และป้ายกำกับที่ไม่รู้จักถูกทิ้ง
  • จำกัดขอบเขตตามองค์กรเสมอ และตามโรงงานสำหรับข้อมูลจริง (ไม่ระบุโรงงาน = ได้ 0 แถว ไม่ใช่ทุกแถว)
  • รันในทรานแซกชันอ่านอย่างเดียว หมดเวลาใน 5 วินาที และจำกัดผลลัพธ์ไม่เกิน 5000 แถว
รูปแบบการตอบมี 3 แบบ (ดูหัวข้อ 1.8) — ตอบด้วยข้อมูล, ถามกลับ, และคำอธิบายเชิงบรรยาย · Board ของข้อมูลจริงเก็บ spec ไม่ใช่ตัวคำสั่ง SQL เปิดใหม่แล้วคอมไพล์ใหม่ทุกครั้ง จึงไม่พังเมื่อโครงสร้างข้อมูลเปลี่ยน

2.6 (ต่อ) ชนิดการตอบ และเพดานการลองใหม่

ทุกคำตอบของ Ask Data เป็นหนึ่งใน 3 ชนิด (turn types) ที่โมเดลเลือกจากคำถาม โดยชนิด "ถามกลับ" และ "คำอธิบาย" จะต่อยอดจากกราฟเดิมโดยไม่ล้างของเก่า

ชนิดการตอบความหมาย
ตอบด้วยข้อมูล
(มี sql)		สร้าง SQL แล้วแสดงผลเป็นกราฟหรือตาราง — แทนที่กราฟ/ตารางเดิม
ถามกลับ
(clarification)		คำถามกำกวม ระบบถามเพื่อระบุให้ชัด ข้อความถัดไปของผู้ใช้ถือเป็นคำตอบ
คำอธิบายเชิงบรรยาย
(prose)		ข้อความสรุป/อธิบายกราฟปัจจุบัน อ้างอิงจากแถวข้อมูลของ SQL ก่อนหน้า ไม่ล้างกราฟเดิม

เพดานการลองใหม่ (bounded retries)

ทุกขั้นจำกัดจำนวนรอบเพื่อให้เวลาและต้นทุนโทเคนคาดเดาได้ เมื่อไม่ผ่านจะ "ลดระดับ" ลงแทนที่จะคืนข้อผิดพลาด

ขั้นตอนเพดาน / พฤติกรรม
แก้ SQL อัตโนมัติสูงสุด 3 ครั้ง (Postgres error → sqlFixup → สร้าง SQL ใหม่)

3.2 การตรวจสอบความถูกต้อง

ความถูกต้องของคำตอบจากผู้ช่วย AI ถูกตรวจเป็นสามชั้น ทั้งในตอนทำงานจริงและในการทดสอบ เพื่อจับข้อผิดพลาดก่อนส่งถึงผู้ใช้ โดยออกแบบให้ "ปลอดภัยเมื่อล้มเหลว" คือถ้าตรวจไม่ได้จะส่งคำตอบเดิมแทนที่จะล้ม

ชั้นการทำงาน
1. ตรวจเชิงกำหนด
(deterministic)		ตรวจฟรีด้วยตรรกะล้วน เช่น เมตริก/ฟิลด์ที่อ้างถึงต้องมีจริงบนเครื่องจักรเป้าหมาย และแผนพรีวิวต้องมีเมตริกครบ หากค้นหาไม่ได้จะข้าม ไม่ทำให้คำขอล้ม
2. ผู้ตรวจ LLM
(judge)		โมเดลตรวจว่าคำตอบตรงเจตนาหรือไม่ (VerifyAnswer สำหรับแชท, ตรวจกราฟ/ตาราง/คำอธิบายสำหรับ Ask Data) ไม่ตรวจชนิดกราฟที่ผู้ใช้ระบุเอง และข้ามเมื่อผลลัพธ์ว่าง
3. การตัดสินผลส่งคำตอบ / ซ่อมหนึ่งรอบ / ถามกลับ — กรณีตรวจไม่ได้ถือว่าผ่าน

สิ่งที่ชุดทดสอบตรวจสอบ

  • Router eval — เจตนาที่ได้ต้องอยู่ในชุดที่คาดไว้ และกรณีคำสั่งกำกวมต้องปฏิเสธอย่างถูกต้อง
  • Bake-off — เครื่องมือแรกที่โมเดลเลือกต้องตรงกับที่คาด พร้อมคะแนน เวลา และโทเคน
  • /ask — SQL ที่สร้างต้องมีคำสำคัญที่คาด และห้ามมีคำสั่งอันตราย (delete/drop/telemetry_raw)
  • เต็มลูป — ทุกเทิร์นต้องจบด้วยข้อความ และต้องมีการเรียกเครื่องมือที่คาด

  • จำกัดเพดานโทเคนต่อการเรียกด้วย AI_MAX_TOKENS (ค่าเริ่มต้น 2048)
  • จำกัดผลลัพธ์เครื่องมือ series/production ที่ ~100 แถว พร้อมค่าสรุป เพราะผลถูกส่งซ้ำทุกรอบ

  • ระยะสั้น — ทดสอบ E2E ฝั่งเบราว์เซอร์, ส่งกราฟจาก /ask ไปเป็นวิดเจ็ต, ส่งออก CSV/PNG
  • ระยะกลาง — จำบริบทยาวขึ้น, บอกสาเหตุเมื่อกราฟว่างเพราะข้อมูลถูกคัดออก, เครื่องมือจัดการกฎแจ้งเตือนแบบพรีวิวก่อนยืนยัน
  • ระยะยาว — streaming, ยุบชุดข้อมูลสาธิตเข้าโครงมาตรฐานให้เหลือตัวสร้างพรอมป์ตเดียว, ปรับจูนตัวจำแนกเจตนาจากบันทึกการใช้งานจริง
จุดบอดที่เหลืออยู่ — ยังไม่มีการทดสอบอัตโนมัติฝั่งเบราว์เซอร์ (E2E) การทดสอบครอบคลุมถึงระดับ HTTP handler และฐานข้อมูลจริงเท่านั้น

ภาคผนวกข. WebSocket

ภาคผนวก ข — โปรโตคอล WebSocket

การเชื่อมต่อแบบเรียลไทม์ใช้ WebSocket ที่เส้นทาง /ws บนพอร์ตเดียวกับ REST (4000) ยืนยันตัวตนผ่านพารามิเตอร์ ?token=<jwt>

ข้อความจากไคลเอนต์ → เซิร์ฟเวอร์

ชนิดความหมาย
subscribeสมัครรับข้อมูลของเครื่องจักรที่ระบุ (ว่าง = รับทั้งหมด)
unsubscribeยกเลิกการรับข้อมูล
pingรักษาการเชื่อมต่อ (heartbeat)

ข้อความจากเซิร์ฟเวอร์ → ไคลเอนต์

ชนิดความหมาย
telemetryค่าเทเลเมทรีล่าสุดของเครื่องจักร
alertเหตุแจ้งเตือนที่เพิ่งเกิด
machine_statusการเปลี่ยนสถานะของเครื่องจักร
ฝั่งเซิร์ฟเวอร์ส่ง ping ทุก 30 วินาที และตั้งกำหนดเวลา pong 60 วินาที เพื่อตรวจจับการเชื่อมต่อที่ขาด แต่ละไคลเอนต์มีคิวส่งข้อมูลแบบบัฟเฟอร์เพื่อไม่ให้บล็อกกัน
